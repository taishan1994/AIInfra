Hy4 preview

腾讯 Hy 团队的新一代旗舰 MoE：用 770B 总参数、49B 激活参数，叠加 Gated DSA、IndexCache、iHC 与原生 MTP，把超长上下文和生产力任务放到同一套架构里。

来源：Tencent Hy Team · Apache 2.0

本文导航它是什么架构拆解注意力与残差能力与评测部署要点工程判断

先说结论

Hy4 preview 的重点不是单纯堆大参数，而是把稀疏激活、稀疏注意力、跨层索引复用、残差多流和投机解码组合起来：总容量保持旗舰级，单 token 只激活 49B 参数，并为 1M context 与代码、办公分析、游戏开发、科研任务做了专门后训练。
770B总参数
49B每 token 激活
1M上下文长度
8路由专家/token

它是 instruct 模型，不是 3090 单卡上的轻量模型；部署侧官方给出了 vLLM 与 SGLang 方案，FP8 版本配合 MTP，目标是把庞大的模型容量转换成可接受的服务吞吐。

架构拆解：容量大，但计算是稀疏的

MoE 主干

主干共 78 层：第 1 层使用标准 dense FFN，剩余 77 层使用 MoE。每层包含 256 个 routed experts 和 1 个 shared expert，每个 token 选择 top-8 routed experts，同时经过 shared expert。770B 更接近总知识容量，49B 更接近一次 forward 的激活计算规模；显存仍需容纳完整权重。

原生 MTP

模型内置 1 个 native Multi-Token Prediction 层，约 10B 总参数、0.7B 激活参数，为 speculative decoding 提供草稿 token，减少逐 token 解码的串行等待。

注意力与残差：三项设计解决三种瓶颈

Gated DSA

轻量 indexer 先判断哪些历史 token 值得进入稀疏注意力，再对候选内容做更完整计算；gate 调节稀疏分支对输出的影响。配置为 32 个 indexer heads、每头 128 维，indexer top-k 为 2048。

IndexCache

跨层复用稀疏索引，避免每一层重复判断“该看哪些 token”。它把长上下文中的重复索引开销变成一次建立、后续复用。

iHC

identity Hyper-Connections 使用 4 条 residual streams。多流残差保留更多独立信息通道，再通过轻量混合实现跨层信息流动；代价是实现和显存管理更复杂。

能力与评测：更偏向“把工作做完”

图 1｜模型卡中的 benchmark 总览。

训练数据围绕软件工程、游戏开发、金融分析和安全专家的实际工作构建，重点覆盖长程开发与验证、多文件办公分析、游戏原型和科研问题。

在 203 个工程任务的内部盲测中，163 位专家给出 Hy4 preview 平均 2.99 分：相较 GLM 5.3 的 2.92，胜/平/负为 46.8%/12.8%/40.4%；相较 Kimi K3 的 2.94，胜/平/负为 51.2%/7.9%/40.9%。这是内部侧评，不应直接等同于公开 benchmark 排名。

部署要点

官方推荐 vLLM 或 SGLang，FP8 版本典型配置使用 8-way tensor parallel、MTP 3 个 speculative tokens、FLASHMLA_SPARSE attention backend，并启用 hy_v4 的 tool-call 与 reasoning parser。

默认 reasoning mode 为 high；简单问答或 RAG 直答可传 reasoning_effort=no_think，避免不必要的延迟。

工程判断

推荐用法

把 Hy4 作为复杂问题处理模型：先由 grep/BM25 做候选发现，再让 Hy4 进行证据整合、冲突判断、长文档分析和工具调用。简单事实查询应关闭 thinking 或使用更快的小模型。

模型卡明确承认它可能过度思考、过度验证，因此产品侧应设计 reasoning budget、工具调用上限、超时和最终答案过滤。
