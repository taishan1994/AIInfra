# DSpark 优化实验记录（2026-08-17）

## 本轮改动

- `flash_decode_dspark.sh`：默认 Decode CUDA Graph 覆盖 `1,2,4,8,16,32,64,128,256`，覆盖 C256；保留 `CUDA_GRAPH_MAX_BS` 和 `CUDA_GRAPH_BS_DECODE` 覆盖入口，避免 51 个连续 batch 桶带来的启动和显存压力。
- `flash_decode_dspark.sh`：默认 `SGLANG_DEEPEP_LL_SPLIT_TOKENS=1024`，用于 DSpark 六 token verify window 的 DeepEP low-latency graph capture。
- `flash_prefill_baseline.sh`：为复现 8 月 5 日旧结果，默认 hidden pool 改为 131072 token，Prefill `mem-fraction-static=0.9`、chunked prefill / `max-prefill-tokens=16384`、`max-running-requests=256`，不再默认传 `prefill-max-requests`。
- Prefill 仍使用 disaggregation queue=8、thread pool=16、hidden thread pool=2；Decode 使用 chunked prefill=1024、`max-running-requests=2048` 和 graph batch `1,2,4,8,16,32,64,128,256`。
- 当前 `MetadataBuffers` 的 DSpark hidden row pool 已恢复为 CPU/host buffer；旧版可复现源码也是 CPU pool。Decode 端默认 `SGLANG_PD_HIDDEN_RECV_POOL_TOKENS=131072`，避免 CUDA hidden pool 对 graph/KV 显存的额外压力，并覆盖 DP4/C512 每 rank 的 hidden window。
- `SGLANG_DSPARK_HIDDEN_ASYNC_ACK=1` 仅作为实验开关保留，默认关闭；本轮因启动阶段 CUDA/NCCL 资源冲突没有形成有效吞吐结果，不能作为验收配置。

该模型 tokenizer 没有 `chat_template`，因此不能调用 `apply_chat_template` 后直接发送空 prompt。已按模型要求显式组装为：

```text
<｜begin▁of▁sentence｜><｜User｜>你是谁？<｜Assistant｜></think>
```

通过 router 的 `/generate` 发送的完整 JSON 已保存为

## 负面对照：Prefill max-running-requests=512

在保持 Decode 不变的条件下，将 Prefill `max-running-requests` 从 256 提高到 512，1024/1024/C512 下降到 **19939.41 tok/s**，低于原 CPU-pool baseline **22712.27 tok/s**。结果保存于 `logs/flash_decode_dspark/aug17_prefill512/c512.jsonl`；因此不采用更大的 Prefill running 上限。

随后在干净服务上实际启用 `SGLANG_DSPARK_HIDDEN_ASYNC_ACK=1` 做 C256 验证，超过默认配置的完成时间仍未结束且没有生成完整结果，已终止并判定为协议挂起；对应的 ACK-fenced 默认路径已恢复并重新通过健康检查。该开关不进入默认配置。

## C512 hidden pool credit A/B

将 Decode `SGLANG_PD_HIDDEN_RECV_POOL_TOKENS` 从 65536 提高到 131072（CPU pool，DP4 下覆盖每 rank 约 128 个 C512 请求），其他配置不变，结果显著改善：

| ISL/OSL | 并发 | output tok/s | total tok/s | mean TTFT | mean TPOT | MTP | 结果 |
|---|---:|---:|---:|---:|---:|---:|---|
| 1024/1024 | 512 | 27147.44 | 54294.89 | 11542.81 ms | 6.72 ms | 28253.34 | 未超过，差 3.9% |

原始结果及健康请求保存在 `logs/flash_decode_dspark/aug17_pool131k/`。相较 65536 pool 的 22712.27 tok/s，吞吐提升约 19.5%，TTFT 降低约 4.0 秒；这确认 C512 的主要问题是 Decode hidden pool credit，而不是单步 decode 计算。

保持 Decode pool=131072，仅将 Prefill hidden pool 从 131072 提到 262144 后，C512 下降到 **20782.30 tok/s**，结果在 `logs/flash_decode_dspark/aug17_pool131k_prefill262k/c512.jsonl`。因此 prefill pool 仍采用 131072，不能简单通过扩大两侧 pool 继续换取吞吐。

补充扫查 Decode pool=98304：C512 为 **21060.74 tok/s**（TPOT 6.03ms，但 TTFT 17.54s），低于 131072 pool 的 27147.44 tok/s，说明 131072 是当前 DP4/C512 的容量拐点。原始结果在 `logs/flash_decode_dspark/aug17_pool98304/c512.jsonl`。

## 联网核对与额外 A/B

查阅 LMSYS 官方 DSpark 部署说明后，官方 DP4 配置是 `moe-a2a-backend=none`、`flashinfer_mxfp4`、`max-running-requests=1024`、CUDA graph 最大 192，并建议比较 `SGLANG_RAGGED_VERIFY_MODE=static|compact`。本机按同口径的 static 配置完成 1024/1024/C512，结果为 **20044.92 tok/s**，低于 DeepEP 配置的 25940.67/27147.44；因此本机 DeepEP 路径更适合当前 PD 压测。官方说明见 <https://www.lmsys.org/blog/2026-07-06-dspark-sglang/>。

官方 compact 配置在本机启动后，C256 压测期间 scheduler 以 exit -3 崩溃，benchmark 收到不完整 HTTP 响应；该结果无 completed 全量，不计入性能比较。上游也有 compact ragged CUDA illegal-access 的公开 issue，因此当前不采用 compact。

DeepEP + overlap ON 的 C256 对照同样无效：仅完成 256/2560 请求，结果文件标记的吞吐不能作为验收数据；已恢复到 overlap OFF 的稳定配置。当前有效默认服务已恢复为 DeepEP low-latency、static verify、overlap OFF、CPU hidden pool、Decode receive pool 131072。

补充 DeepEP `max-running-requests=1024` 的有效 C256 对照为 **19806.65 tok/s**（完整 2560/2560），低于默认 2048 的 **24766.66 tok/s**，因此保留 2048；对应结果在 `logs/flash_decode_dspark/aug17_matrix_best/isl1024_osl1024_c256_maxrun1024/result_maxrun1024.jsonl`。

## 全部方案审计（截至 2026-08-17）

本节集中记录本轮及前序实验，明确区分“完整有效结果”和“无效/挂起/崩溃”。吞吐统一采用 benchmark 的 `output_throughput`，只有 `completed=10×并发` 的结果才进入有效比较。

指标定义：`output tok/s` 为 `output_throughput`，`total tok/s` 为 `total_throughput`（输入 token + 输出 token），TTFT/TPOT 分别为 benchmark 的 `mean_ttft_ms` / `mean_tpot_ms`。MTP 历史表只记录了 output tok/s，原始资料没有 total tok/s、TTFT、TPOT，因此以 `—` 表示，不反推。

### 当前结论

1. 已稳定证明 DSpark 在 C256 超过 MTP：当前最佳为 **24766.66 vs 20826.03**。
2. C512 的单次干净链路最佳仍为 **27889.71 output tok/s、55779.41 total tok/s、TTFT 10866.71 ms、TPOT 6.76 ms**，对比 MTP output `28253.34` 仍低约 1.29%；hidden2 最终复测仅 **20793.16 output tok/s、41586.33 total tok/s、TTFT 17626.49 ms、TPOT 6.16 ms**，尚未形成稳定复现。
3. 本轮新增验证表明：clean strict pool131072 配合 hidden thread pool=8、buffer512、transfer queue64、Prefill max/chunk16384 是目前 A/B 最优；pool=4 为 `25023.20`，pool=8 为 `27217.35`，pool=16 回落到 `25795.56`。Prefill max/chunk32768、queue/thread128/128、buffer1024、transfer queue128 均退化；运行状态波动仍是主要问题。`MC_IB_PCI_RELAXED_ORDERING=1`、Prefill queue/thread 32/32、Prefill pool524288、两侧 pool524288、Decode recv=65536、Decode `deep_gemm` 或 recovered SPS table 都不能超过 MTP。
