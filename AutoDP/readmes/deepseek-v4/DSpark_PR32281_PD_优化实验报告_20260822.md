# DSpark PR #32281 参考适配与 PD 分离性能实验报告

> 实验日期：2026-08-21
>
> 整理日期：2026-08-22
>
> 实验目标：在原始 SGLang v0.5.16 的 PD 分离部署上切回 DSpark，参考 [SGLang PR #32281](https://github.com/sgl-project/sglang/pull/32281) 完成适配，并与原始 baseline 对比。

## 1. 结论

本轮 DSpark 服务在 Prefill/Decode PD 分离、Mooncake/RDMA、DeepEP `low_latency` 和 Decode CUDA Graph 配置下完成了 8 组测试。8 组的请求均全部完成，Total tok/s 均超过原始 baseline：

- 1024 输入：提升 140.2%～193.1%；
- 8192 输入：提升 5.2%～178.3%；
- 8192 输入高并发仍受 Prefill 排队和 hidden transfer 影响，虽然吞吐超过 baseline，但 TTFT 显著增大。

本轮使用的是 DSpark 路径，不包含 Waterfill、LPLB、TBO、MTP 等优化开关。Decode 使用 DeepEP `low_latency`，并开启 Decode CUDA Graph；由于 DeepEP low-latency 单 rank dispatch capacity 限制，正式运行采用 graph batch 最大 128。

## 3. 参考 PR 的适配内容

PR #32281 的主体是 Pipeline Parallel + DSpark 适配。本实验是 PD 分离、`pp_size=1`、Decode `dp_size=4`，因此没有直接引入 PP relay 逻辑，而是移植了对当前拓扑有价值的三类改动。

### 3.1 将 dense draft embedding 折叠进 draft graph

在 `python/sglang/srt/models/dspark.py` 中保留 target 的 embedding，并增加 `forward_embed()`，使 DSpark draft 的 embedding 计算能够进入 draft CUDA Graph，而不是每个 decode step 单独走 eager 路径。

对应 PR 思路：`Fold dspark dense draft embedding into draft graph`。

### 3.2 合并 dense draft 的上下文 KV projection

在 `dspark.py` 中增加 stacked context KV projection：当权重布局满足条件时，将多个目标层的 context KV projection 合并为一次 GEMM；不满足条件时保留逐层 fallback，保证功能兼容。

对应 PR 思路：`Stack dspark dense draft per-layer ctx KV projection into one GEMM`。

### 3.3 修正 DP/EP 元数据

在 `dspark_draft.py` 的 DP MoE 同步元数据路径中补充：

- `original_global_num_tokens_cpu`；
- 当前 DP rank 的 local token 数；
- `num_token_non_padded` 及 CPU 版本。

这保证 DSpark verify 在 DP attention + EP/DeepEP 下能够区分全局 padded token 数和本 rank 的有效 token 数。

## 4. 为当前 PD 分离补充的稳定性修复

### 4.1 首请求 draft anchor 初始化

当 PD 请求首次进入 Decode 时，`batch.spec_info` 可能为空，原路径无法构造 DSpark draft input。当前在 `spec_utils.py` 创建 idle `DFlashDraftInputV2`，并在 `dspark_worker_v2.py` 中从 `batch.input_ids` 或请求最后一个有效 token 建立首个 draft anchor。

### 4.2 DSpark 与 DP Attention 的兼容开关

移除了原始 speculative hook 对 `moe_a2a_backend != none` 的硬拒绝，使 DSpark 可以和 DP Attention + DeepEP low-latency 一起运行。

### 4.3 多请求 merge 崩溃修复

完整压力测试前发现：运行 batch 已有 DSpark `spec_info`、新合并请求没有 `spec_info` 时，`ScheduleBatch.merge_batch()` 会调用 `merge_batch(None)`，触发：

```text
AttributeError: 'NoneType' object has no attribute 'reserved_seq_lens_cpu'
```

在 `python/sglang/srt/managers/schedule_batch.py` 中增加了 None-safe 合并逻辑：

- 两侧均有 speculative state 时才执行合并；
- 一侧为空时重置聚合 speculative state；
- 下一次 Decode step 由 worker 根据合并后的 batch 重新建立 state。

修复后先通过 1024/1024/concurrency 16 回归，再执行完整矩阵。

## 5. DeepEP 适配方式

DSpark 的 verify batch 可能包含 CUDA Graph padding；DeepEP low-latency 要求 activation、top-k ids 和 top-k weights 的 token 首维一致。因此当前路径：

1. 根据 hidden size 计算有效 flat rows；
2. 对 activation 和 top-k 元数据使用一致的 leading shape；
3. oversized dispatch 按 `SGLANG_DEEPEP_LL_SPLIT_TOKENS=1024` 控制；
4. 使用 DeepEP 当前版本支持的 combine 参数；
5. 在 Decode CUDA Graph 中预先捕获 1、2、4、8、16、32、64、128 batch。

尝试捕获 graph256 时，6-token verify window 会使 dispatch rows 超过当前 DeepEP low-latency 每 rank 的 1024 上限，出现：

```text
x.size(0) == topk_idx.size(0) and x.size(0) <= num_max_dispatch_tokens_per_rank
```

因此本轮正式配置选择 graph128。Graph128 仍然是 Decode CUDA Graph，不是关闭 CUDA Graph；超过 128 的运行 batch 由运行时调度到可用 graph/eager 路径。后续若要进一步提升高并发，需要实现真正的 DeepEP verify batch 分块，而不是只设置环境变量。

### 7.1 结果解释

- 短输入下，DSpark 的 draft/verify 和 DeepEP low-latency 组合明显超过 baseline，尤其是 concurrency 512。
- 8192 输入低并发也超过 baseline，说明 PD hidden transfer、首请求初始化和长上下文路径已经能够稳定工作。
- 8192 输入高并发的 Decode TPOT 仍较低，但 TTFT 达到 28.65 s/62.17 s，说明主要瓶颈转移到 Prefill 排队、hidden transfer 和 Decode admission，而不是单步 decode 计算。
- 因此不能只用 Total tok/s 判断长输入体验；后续优化应优先降低 hidden transfer 排队和 TTFT。

## 9. 后续优化方向

1. 实现 DeepEP low-latency verify batch 的真实分块，使 graph256 在 DSpark 6-token verify 下可用。
2. 对 hidden receive、target hidden-KV write 和 DeepEP dispatch 建立 request-scoped ready/write-complete event，减少高并发长输入 TTFT。
3. 对 8192/C256、C512 分别扫描 hidden pool、transfer queue、Prefill chunk 和 Decode graph tier，并至少重复两轮。
4. 继续以原始 baseline 为唯一正式对照，同时记录 Out tok/s、Total tok/s、TTFT、TPOT 和 completed，避免把 partial result 当作性能结果。
